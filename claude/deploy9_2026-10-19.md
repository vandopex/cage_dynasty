## §4 Findings

(a) **error.log baseline captured pre-reload for the first time.** Deploy #8 §4a was explicit about the missing step-3 baseline; deploy #9 closed it. Pre-reload fetch at step 3 and post-reload fetch at step 11 produced byte-identical files (148 lines, 14399 bytes, `diff` output empty). This is a stronger assertion than deploy #8's timestamp-only test, which showed zero `2026-09-22` lines but had nothing to subtract from. v1.2 candidate (see §5).

(b) **PA respawned between deploys with no deploy.** server.log L100 shows `2026-10-18 00:07:19 gracefully (RE)spawned uWSGI master process (pid: 1)` — three days after deploy #8's reload at `2026-09-22 04:49:05` (deploy8 §3 row 9), and sixteen days before deploy #9's reload at `2026-10-19 21:26:13`. No deploy fired between. Likely explanations: a browser console session triggered an implicit reload, or PA infrastructure cycled uWSGI as part of routine maintenance. Not a phantom deploy — the SHA gate at step 7 shows PA was at prevPA `20b828a` immediately before deploy #9, meaning no code change rode along with that respawn. File for pattern-watch; next similar event, note the clock gap and the SHA stability across it.

(c) **Console 47103182's CWD is `cage_dynasty_web/`.** The warm-check prompt showed `21:21 ~/cage_dynasty/cage_dynasty_web (main)$` — not `~/cage_dynasty`. Every console command this deploy prepended `cd ~/cage_dynasty && …` to reach repo root. Prior deploys silently depended on repo-root CWD; this deploy made it explicit. Procedure change candidate: step 3's command block should always include `cd ~/cage_dynasty &&` as a prefix regardless of prompt-visible CWD. v1.2 candidate.

(d) **Console poll buffers carry earlier markers.** Step 7's `get_latest_output` poll contained `GATE5DONE` (from the step-5 pull) at the top of its output, before the step-7 marker `GATE7DONE`. The poll returns the latest N bytes of console history, not just what landed since the last poll; a naive `grep -c GATE_DONE` would double-count. This deploy's parse used `rfind("GATE7DONE")` to anchor on the step's own marker — but the risk is latent. Any future gate that checks for "a marker" rather than "this step's marker" can misread. v1.2 candidate.

(e) **Step 12 VACATED-REIGN1 row can't be forced on a fresh save.** `move_weight_class` is player-roster only; `resolve_champion_injury_decision` needs a player-camp champion; the 25-week injury auto-vacate at the "Belt vacating — champion injured too long" marker fires on AI champions probabilistically. Van advanced to week 10 and no `TITLE VACATED` headline appeared, which is normal — fresh saves rarely trip the 25-week threshold inside a 10-week window. The row is recorded as INFO ("not exercised in browser — probe v3 evidence stands"). Probe v3 (claude/vacated_reign1_gate0_2026-10-17.md §5) remains the primary engine evidence; the browser row is confirmation-when-observed, not a required gate. v1.2 candidate: INFO-row shape for browser rows that can't be forced should be standard.

## §5 v1.2 candidates added by #9

Candidates for `deploy_procedure.md` v1.2; not procedure until landed.

* **Fold the error.log baseline into step 3 as a standard sub-step.** Pre-reload Files-API fetch of `/var/log/<domain>.error.log` → `/tmp/error_baseline.log`. Step 11 then runs `diff` against the real file, not a timestamp comparison. §4(a) closes deploy8 §4a; make it the standard shape, not a one-time catch-up.
* **Step 3 command block prepends `cd ~/cage_dynasty &&`.** Console CWD is not guaranteed to be repo root (§4(c)). Explicit `cd` prevents a silent prompt-dependent dependency.
* **Gate parsers anchor on the step's own marker.** Console poll buffers accumulate (§4(d)). Use `rfind("GATE<N>DONE")` or equivalent to anchor; never `grep -c "GATE_DONE"` or substring match "a marker".
* **Browser rows that can't be forced on a fresh save use the INFO shape.** Record what Van observed in the window; if the observational signal didn't fire, cite the primary engine evidence (probe filing + §) and mark INFO, not FAIL. §4(e).
